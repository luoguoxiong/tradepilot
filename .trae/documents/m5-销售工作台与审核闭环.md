# M5 实现计划：销售工作台与审核闭环

## Context

排期文档（前端开发排期计划.md L79-88）M5 共 6 任务（22 人日）：DraftEditor(Tiptap)、06 三栏工作台、AI Copilot 面板、ApprovalCard+12 审核中心、waiting_approval 全局通知、邮件沙箱预览。出口标准：E2E 用例③④（发送→待审→编辑后批准）mock 口径可走。

前置事实（已核实）：
- 路由 `/inbox`、`/approvals` 均为 placeholder 占位（router/routes/modules.ts L54-64, L90-95）
- API 层无 conversations 模块；approvals 仅有 summary；ESLint `vue/no-v-html: error`
- `useTaskStream` 已预留 `onStatus(status, linkedApprovalId)` 回调；notifyStore 15s 轮询已就绪
- keep-alive 白名单已登记 `ApprovalsView`（`InboxView` 需补）；vite manualChunks 仅 element-plus
- 依赖缺 `@tiptap/*`；已有 dompurify/@vueuse/core
- CRM 删除流 mock（handlers/customers.ts DELETE）返回裸 `nextId('appr')` 但审批单未持久化——需打通

## 关键设计决策

| # | 决策 | 结论 |

| 2 | DOMPurify 落点 | 新建 `utils/sanitize.ts`（ALLOWED_TAGS 基础集 + a[href] 限 http/https/mailto）；用于 iframe srcdoc 前消毒 + AI content 防御消毒 |

| 5 | 消息翻页 | 客户端窗口化 + scrollAnchor（首屏尾部 30 条，向上 prepend 30），不引入虚拟滚动（阈值 200 未触及） |

## 核心联动：审批闭环（mock 层数据源统一）

新建 `mocks/data/approvals.ts` 作为审批记录唯一事实源：
- `registerCustomerDeleteApproval(customerId)` — CRM DELETE/batch-delete 改调此函数换真实 approvalId
- `approveCustomerDelete` → 从 mockCustomers 真删 + summary 计数自然归零；`rejectCustomerDelete` → deleteLocked=false 解锁
- `approveEmailSend` → 会话消息 status draft→sent；`registerEmailSendApproval(context, aiProposal)` — 06 send 分支 B 调用
- 种子：2 条 email_send（其一 expiresAt 已过期，演示超时终态禁用）+ 1 条 customer_delete（绑定 cus_8，固定 ID `appr_8`）
- summary handler 中静态 `emailSend = 2` 常量删除，改由 mockApprovals pending 派生
