## 1. 认证（Authentication）

### 1.1 登录注册（MVP 仅邮箱+密码，16 §7.3）

| 接口 | 行为要点 |
|---|---|
| `POST /auth/register` | ① Zod 校验（密码 ≥ 8 位）② bcrypt 哈希（cost 12）③ 单事务种子初始化（[02 §10](./02-数据访问层设计.md)）：org（含 timezone/defaultCurrency/defaultLanguage 三默认值）+ admin 账号 + role_permission×3 + 默认跟进策略/步骤 + 6 预置员工（sop_template + ai_employee）+ ai_model_setting ④ 返回 token + `onboarding.currentStep=1` |
| `POST /auth/login` | 统一失败文案「邮箱或密码错误」返回 `40101`（防账号枚举，无论账号不存在/密码错/成员 disabled）；`loginType` 字段预留（MVP 仅 `password`） |
| `POST /auth/invitations/accept` | 邀请 token 校验 → 补密码 → `member_status: invited → active` |
| `POST /auth/refresh` | 见 §1.3 |

- 注册即创建 org + 管理员（一人企业合法）；`user_account` 唯一性按 `UNIQUE(org_id, email)` + 全局登录按 email 查找（同 email 可属于不同 org？——**MVP 单邮箱单企业**：全局唯一 email，登录时直接定位 org，JWT 带 orgId）。

### 1.2 密码与会话安全

- bcrypt cost 12；登录限流：同账号 5 次/15min、同 IP 30 次/15min（Redis 计数），超限 `42901`（[08 §3](./08-安全设计与合规.md)）。
- 停用即时失效：成员停用（16 FR-03「停用即时失效会话与 API 凭证」）→ Redis 写 `disabled:{userId}` 标记，JwtAuthGuard 每请求校验（缓存 30s）；角色变更即时生效——权限实时读 `role_permission`，JWT 只带不可变标识（userId/orgId）+ 冗余 role（角色变更时 refresh 或直接以库内为准，实现取「库内为准」）。

### 1.3 JWT 策略

| 项 | 决策 |
|---|---|
| 算法 | HS256（MVP 单密钥 `JWT_SECRET`；头部预留 `kid`，支持后续 RS256 轮换） |
| Payload | `{ sub: userId, orgId, role }`；不含敏感信息 |
| 有效期 | access 2h + refresh token 14d（Redis 存储可撤销，`refresh:{userId}:{jti}`） |
| 携带 | `Authorization: Bearer`；SSE 端点支持 `?token=` 查询参数（EventSource 无法带 header） |

## 2. RBAC 角色权限

### 2.1 三角色基线（16 §2.7 权限矩阵）

| 资源 | admin | manager | sales |
|---|---|---|---|
| 客户 | all | team | self |
| 报价（P1） | edit/approve | edit/approve | view |
| 审批 | 全部类型 | 可配类型 | — |
| 设置 | manage | view | none |

- `role_permission` 行存矩阵 jsonb（`UNIQUE(org_id, role)`）；Guard 读库不读死配置，支持后续细化。
- 组织级操作（成员管理、企业信息、AI 模型、外发规则）仅 admin；AI 员工配置、知识删除/重试 admin+manager。

### 2.2 Guard 链（全局注册，模块内声明式启停）

```text
JwtAuthGuard（身份 + 停用检查）
  → RolesGuard（@Roles('admin','manager') 装饰器；未标注 = 三角色可访问）
  → ResourceGuard（资源级：owner/团队边界，§4）
```

- 关键路由约束（对齐接口文档标注）：AI 员工创建/修改、审批处置、设置类 = admin/manager；客户阶段推进、订单变更 = 服务层禁 AI 身份（§5）。
- P1 开放 API：`ApiKeyGuard` 替代 JwtAuthGuard——`Authorization: Bearer tpk_...` → sha256 查 `api_key.key_hash` → 校验 `scopes` 与 `status='active'`；停用成员名下 Key 同步失效。

## 3. 组织隔离与上下文

- JWT 解出 `orgId` 后注入 RequestContext（ALS）；所有 repository 查询经 `withOrg(orgId)` 打开 RLS 会话（[02 §4.3](./02-数据访问层设计.md)），**业务代码不出现手写 `where orgId`**（RLS 承担），仅日志类跨表聚合仍显式带 org 条目以走索引。
- worker 侧：任务 job 携带 `orgId`，TaskRunner 构造同等上下文；队列 job 数据只含 ID 引用，不内嵌业务快照（以库内当前值为准）。

## 4. 数据范围（scope=self|team|all）

### 4.1 scope 判定

```typescript
// packages/core/scope.ts —— 单一实现点
resolveScope(role, resourceConfiguredScope): 'self' | 'team' | 'all'
// 角色上限：sales→self、manager→team（可配 all）、admin→all
// 请求参数 scope 超出角色上限 → 40301（总览 §4.4）
```

### 4.2 查询注入

```typescript
// packages/db/src/scope.ts
applyOwnerScope(qb, ctx, { ownerColumn = 'owner_id', teamColumns }): QueryBuilder
// self  → where owner_id = ctx.userId
// team  → where owner_id in (团队成员集合，manager 的 team = 本 org 全部成员 MVP 简化，P1 引入团队分组)
// all   → 不追加
```

- 适用表：`customer / quotation / sales_order / follow_up_task / conversation`（经 customer 归属）等带 `owner_id` 资源；`ai_lead` 共享池不受 scope 限制（获客成果 org 级共享，03 §4）。
- 单资源读/写前 `assertResourceAccess(row, ctx)`：越权 `40301`；列表与详情共用同一函数防旁路。
- owner 变更：仅 admin/manager（05 需求决议），写 `customer_activity(activity_type='owner_change')`。

## 5. AI 身份与操作边界

| 规则 | 实现 |
|---|---|
| AI 触发的写操作以 `operator_type='ai'` + employeeId 留痕 | `customer_activity` / `approval_log` 写入时从 ToolContext 取 `operatorType`（[01 §6.6](./01-工程结构与编码规范.md)） |
| AI 不可调用：客户阶段推进、订单变更、身份变更（potential/formal） | 这些 service 方法声明 `humanOnly()` 元数据；工具层（crm_write 等白名单工具）不暴露对应能力，**白名单机制天然隔离**（[05 §3](./05-AgentRuntime与LLM网关.md)） |
| AI 不自动加入 CRM、不自动对外发信 | 工具实现约束：`crm_write` 仅写 ai_lead 池；`email_send` 必经 Approval Gate |
| AI 不改 `owner_id` | 同上，工具入参 schema 不含 ownerId 字段 |

## 6. 邮箱邀请与成员生命周期

```text
POST /members/invitations（admin）→ 生成邀请 token（单次、7d，Redis）
  → 邮件发送邀请链接 → 接受（§1.1）→ active
停用 → disabled（会话+API Key 即时失效）→ 可重新启用
角色变更 → 即时生效（后续请求按新角色裁剪）
```

- 邀请角色必选 admin/manager/sales；同 org 邮箱唯一（`UNIQUE(org_id, email)`）。
