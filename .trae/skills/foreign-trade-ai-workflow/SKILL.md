# 外贸AI项目全流程编排工作流（Foreign Trade AI Workflow Orchestrator）

**总控职责**：一次输入，端到端串联三个专家 Skill，按流水线自动推进，产出完整交付物并**按目录迭代沉淀**。你（当前Agent）是流水线的总指挥，每个阶段**必须先调用对应 Skill 再干活**。

```text
需求输入
  │
  ▼
┌─────────────────────────────────────────────────┐
│ Phase 1 产品打磨  → 调用 Skill: foreign-trade-ai-product-expert │
│ 沉淀：prod/{feature}/ 诊断报告 + PRD              │
├─────────────────────────────────────────────────┤
│ 🚪 Gate 1：用户确认 PRD（必须暂停等确认）          │
├─────────────────────────────────────────────────┤
│ Phase 2 开发实现  → 调用 Skill: foreign-trade-ai-dev-expert      │
│ 沉淀：server/docs + web/docs 技术方案 + server/ + web/ 代码│
├─────────────────────────────────────────────────┤
│ 🚪 Gate 2：用户确认实现方案/代码（必须暂停等确认）   │
├─────────────────────────────────────────────────┤
│ Phase 3 测试验证  → 调用 Skill: foreign-trade-ai-qa-expert      │
│ 沉淀：test/{feature}/ 测试计划 + 报告 + 评估集      │
├─────────────────────────────────────────────────┤
│ Phase 4 交付总结：汇总产物路径 + 遗留风险 + 下轮迭代建议│
└─────────────────────────────────────────────────┘
```

## 一、沉淀目录约定（核心：目录即资产，迭代只增不丢）

项目根目录四个业务目录，各 Skill 按此约定读写：

```text
tradepilot/
├── prod/                        # 产品文档沉淀（产品阶段产出）
│   └── {feature}/
│       ├── _state.md            # 工作流状态（断点续跑依据）
│       ├── diagnosis.md         # 诊断报告（迭代时追加修订记录）
│       └── prd.md               # PRD（含修订记录，v2/v3在文件内追加）
├── server/                      # 后端项目位置（开发阶段在此编码演进）
│   └── docs/{feature}/          # 后端技术方案：design-v1.md, design-v2.md…（每个迭代一份）
├── web/                         # 前端项目位置（开发阶段在此编码演进）
│   └── docs/{feature}/          # 前端技术方案：design-v1.md, design-v2.md…（每个迭代一份）
└── test/                        # 测试专用
    └── {feature}/
        ├── eval-sets/           # golden set 评估集（badcase持续回流，只增不删）
        ├── test-plan.md          # 测试计划（迭代时更新）
        └── test-report-v1.md     # 每轮回归一份新报告，v2/v3…保留历史
```

**迭代沉淀规则**：

1. **同一需求再次打磨** → 先读 `prod/{feature}/` 既有文档，在文件内追加「修订记录」（版本号+日期+变更点+触发原因），不覆盖历史结论；测试报告则新增 `test-report-v{n}.md`；前后端技术方案则分别在 `server/docs/{feature}/`、`web/docs/{feature}/` 新增 `design-v{n}.md`
2. **新需求** → `prod/`、`test/`、`server/docs/`、`web/docs/` 下新建 `{feature}` 目录；代码直接演进 `server/`、`web/`（由 git 管理历史）
3. **评估集只增不减**：每轮测试的 badcase 必须回流 `test/{feature}/eval-sets/`，标注来源轮次
4. **首轮初始化**：`server/`、`web/` 为空时，Phase 2 按开发 Skill 的技术栈基线初始化项目骨架

### \_state.md 格式

```markdown
# 工作流状态

- 需求原文：...
- 当前阶段：phase1 / gate1 / phase2 / gate2 / phase3 / done
- 迭代轮次：v1 / v2 / ...
- 阶段历史：[{阶段, 完成时间, 产物路径}]
```

### 断点续跑

每次启动工作流时：若 `prod/{feature}/_state.md` 已存在，读取当前阶段**从断点继续**，不重复已完成阶段；若用户重新描述需求且与历史不符，询问"新需求开新 feature 目录，还是作为既有需求的迭代轮次"。

## 二、各阶段执行规则

### Phase 1：产品打磨

1. **先调用 `Skill: foreign-trade-ai-product-expert`**，按其方法论执行
2. 执行其 Step 1-5 工作流：需求澄清 → 五维诊断 → 问题定位 → 打磨方案
3. 沉淀 `prod/{feature}/diagnosis.md` 与 `prod/{feature}/prd.md`（遵循产品Skill的输出模板）
4. PRD 中必须写明「AI行为边界」（能做什么/绝不做什么/不确定时怎么办），这是后续开发与测试的依据
5. 完成后更新 `_state.md` → `gate1`

### 🚪 Gate 1（强制人工门禁）

- 用 AskUserQuestion 请用户确认 PRD，明确选项：**通过并进入开发 / 修改后重跑 / 终止**
- 信息不足时在 Phase 1 内先追问（遵循产品Skill的必问清单），不要带着模糊需求过门
- **未获用户确认前，禁止开始写任何业务代码**

### Phase 2：开发实现

1. **先调用 `Skill: foreign-trade-ai-dev-expert`**，按其工程规范执行
2. 遵循其 Step 1-5 工作流：业务规则确认（以已确认PRD为准）→ 技术方案 → 编码 → 验证
3. 后端代码写 `server/`，前端代码写 `web/`；项目为空时按开发 Skill 技术栈基线初始化骨架；已有代码则先读既有结构，遵循项目约定
4. 红线检查：金额/HS编码/汇率实现是否走结构化数据源；单证是否模板+校验
5. 技术方案按迭代落盘：后端写 `server/docs/{feature}/design-v{n}.md`，前端写 `web/docs/{feature}/design-v{n}.md`（前后端独立成文，方案内注明对应 PRD 版本），完成后更新 `_state.md` → `gate2`

### 🚪 Gate 2（强制人工门禁）

- 汇报实现方案与代码变更清单（server/ 与 web/ 分别列出），请用户确认：**通过并进入测试 / 修改 / 终止**
- 用户明确说"全自动不用确认"时，可在 Gate 1 记录 `skip-gates: true`，之后自动放行（但 P0 红线问题仍必须人工知晓）

### Phase 3：测试验证

1. **先调用 `Skill: foreign-trade-ai-qa-expert`**，按其测试方法论执行
2. 执行其 Step 1-5 工作流，重点是：
   - 红线场景 100% 覆盖（报价数字、单证一致性、汇率时点）
   - 确定性逻辑跑精确断言；AI生成点跑要素断言（可执行的写成自动化用例）
   - 输出 Go / No-Go 结论
3. 沉淀 `test/{feature}/test-plan.md`、`test/{feature}/test-report-v{n}.md`（本轮次版本号），评估集入 `test/{feature}/eval-sets/`
4. **No-Go 时**：定位缺陷归属（开发问题→回 Phase 2 修复后重测；需求问题→回 Gate 1 报告用户），修复循环最多 2 轮，仍不达标则停下来向用户汇报决策
5. 每轮 badcase 回流评估集后，在 `_state.md` 迭代轮次 +1

### Phase 4：交付总结

- 汇总产物路径（prod/{feature}/ 文档 + server/docs、web/docs 技术方案 + server/web 代码变更 + test/{feature}/ 报告）与核心结论
- 列出遗留风险（P2/P3未修复项）与**下一轮迭代建议**（基于本轮 badcase 与用户反馈）
- 更新 `_state.md` → `done`

## 三、跨阶段传递契约（保证流水线不串味）

| 传递物   | 来源 → 消费方                                          | 关键字段                                            |
| -------- | ------------------------------------------------------ | --------------------------------------------------- |
| PRD      | prod/{feature}/prd.md → Phase 2/3                      | 目标用户、AI行为边界、验收标准                      |
| 技术方案 | server/docs/{feature}/ + web/docs/{feature}/ → Phase 3 | 架构分层（哪些是确定性逻辑=精确测试对象）、降级路径 |
| 测试报告 | test/{feature}/ → 用户/回环                            | Go/No-Go、红线结果、Bug分布                         |
| 评估集   | test/{feature}/eval-sets/ → 跨轮次复用                 | 持续扩充的golden set，防效果回退                    |

**回环规则**：任何阶段发现上游产物问题（如开发发现PRD业务规则矛盾、测试发现设计缺陷），在当前产物中标注「上游问题」，回到对应 Gate 由用户决策，不允许擅自改上游产物继续跑。

## 四、行为准则

1. **先调 Skill 再动手**：进入新阶段第一动作是调用对应 Skill，让专家方法论生效，而不是凭总控自己发挥
2. **门禁不可跳过**：Gate 1/Gate 2 默认强制人工确认；仅当用户显式授权"全自动"才可放行
3. **一切产物落盘且迭代沉淀**：会话可以中断，文件是唯一可信状态；重跑既有需求 = 迭代（追加修订记录/新版本报告），不是推倒重来；每阶段结束即更新 `_state.md`
4. **进度透明**：每完成一个阶段，向用户输出简短进度摘要（当前阶段/产物路径/下一步）
5. **不过度执行**：小需求（如只改一个Prompt）可裁剪流程——直接路由到对应单阶段执行，用户说"只做产品/只做开发/只做测试"时尊重指令，不强行跑全流程
