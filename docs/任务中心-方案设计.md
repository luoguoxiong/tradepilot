## 1. 定位与职责

### 1.1 在整体架构中的位置

任务中心模块是**控制面**：不执行任务，只负责「状态机写库 + 队列投递/撤销 + 事件推送」。

```
前端 ──REST──> tasks.controller ──> tasks.service ──┬─> PostgreSQL (ai_task / step / log，RLS 租户隔离)
     ──SSE───> task-stream.controller ──┐           └─> BullMQ 队列 (TaskEnqueuer)
                                        │                       │
                                        └─ Redis Pub/Sub <──────┴─> Worker (TaskRunner) 执行图、写日志/终态
```

设计依据（`后端技术方案文档/04-任务调度与队列.md`）：§1 队列与并发、§2 入队判定、§3 调度、§5 状态机与领取、§6 SSE；接口契约见 `产品需求文档` 接口 14 §3。

### 1.2 文件职责

| 文件 | 职责 |
|---|---|
| `tasks.module.ts` | 装配两个 Controller + `TasksService`（导出供其它模块复用 `create`） |
| `tasks.dto.ts` | Zod 契约（新建/列表筛选/转人工/批量），编译期类型 + 运行期校验同源 |
| `tasks.controller.ts` | REST 端点，只做参数校验 + 取 `orgId/sub` + 委派 |

依赖方向干净：**Controller → Service → packages（db / runtime / shared / core）**，Service 不反向依赖 Controller。

- **租户隔离下沉到 DB**：所有查询走 `withOrg(db, orgId, fn)`，事务内 `set_config('app.org_id')` 打开 PG RLS（`packages/db/src/tenant.ts:23`）。Service 里显式写的 `eq(aiTask.orgId, orgId)` 是索引友好 + 语义显式，不是唯一的安全屏障。

## 3. 数据模型与状态机

三张表（`packages/db/src/schema/02-ai-task.ts:88`）：`ai_task`（主表 + `retry_of` 自引用 + `linked_approval_id` + `outputs` jsonb）、`ai_task_step`（`seq` 有序步骤）、`ai_task_log`（执行流水）。

```
                 ┌──────────────── pause ────────────────┐
                 ↓                                        │
  create ──> scheduled ──直投/调度──> running ──审批挂起──> waiting_approval
                 ↑                     │  │                    │ approve / reject
                 └───── resume ────────┘  │                    ↓
                      (无检查点)          ├────> completed / failed ──> (retry = 新任务)
                                          └────> canceled (终态)
```

三条必须遵守的语义约束：

1. **落库一律 `scheduled`，`running` 只能由 Worker 的 `Runner.claim` 独占置位并补 `started_at`**（04 §5.2）。杜绝「`running` + `started_at` 为空」的不可恢复直投态（历史故障 M3-01 冻结整个 org 并发的根因）。
2. **员工并发 = 1**：`running` 与 `waiting_approval` 均占员工位（`EMPLOYEE_OCCUPYING_TASK_STATUSES`）；**org 并发 = 10，只统计 `running`**（挂起不占 org 额度）。
3. **`retry` 不是重启旧任务，而是创建新任务**，`retry_of` 溯源、复制 input，日志不迁移。

## 4. 核心设计决策

### 4.1 入队判定三段式 + 事务提交后再投递

`server/apps/api/src/tasks/tasks.service.ts:116`：

```ts
const canRun = (empBusy?.n ?? 0) === 0 && (orgRunning?.n ?? 0) < ORG_CONCURRENCY_LIMIT;
const due = !scheduledAt || scheduledAt.getTime() <= Date.now();
const immediate = canRun && due;
...
// 事务提交后再入队：若在事务内入队，Worker 可能先于提交消费 → probe 落空 → 任务永久卡死（M3-01）
if (immediate) {
  await this.enqueuer.enqueueTask(taskId, dto.type as TaskType);
}
return { taskId, status: immediate ? 'running' : 'scheduled' };
```

- **并发判定在事务内只读取快照**（`count(*)`，不加行锁），极端并发下可能超发。真正的互斥由 Worker `claim` 的 `UPDATE ... WHERE status='scheduled' RETURNING`（CAS 乐观锁）兜底 —— **API 侧重吞吐，Worker 侧保证正确性**，典型两层防御。
- **队列消息必须在事务提交之后发**：否则 Worker 可能先于提交消费，读不到未提交行 → 任务永久卡死。这是「数据库 + 队列」双写最经典的坑。
- **未来定时任务即使并发空闲也保持 `scheduled`**，由 Dispatcher / delayed job 到点投递。
- 响应 `status` 是**语义化**的：`running` = 已投递待执行（DB 里仍是 `scheduled`），`scheduled` = 排队。前端据此决定直接开 SSE 还是显示「排队中」。

### 4.2 操作类接口统一四段式

`pause` / `resume` / `cancel` / `transfer-to-human` 共用同一骨架：

```
① 事务内：读任务 → 前置状态校验（源状态非法 → 409 conflict）
② 事务内：CAS 更新 UPDATE ... WHERE id=? AND status IN (允许的源状态) RETURNING
          returning 为空 → 已被并发抢改 → 409「请刷新后重试」
③ 事务内：写 ai_task_log 留痕 + 员工位联动（releaseEmployeeIdle / 置 working）
④ 事务提交后：队列清理或重投（removeTask / enqueueResumeFromPause）+ SSE 推送 status / done
```

**为什么 ④ 必须在提交后？** Redis 侧操作不可回滚；若事务内先发 SSE、随后回滚，客户端会收到一个从未存在过的状态。

| 操作 | 允许源状态 | 目标态 | 队列 | 员工位 | SSE |
|---|---|---|---|---|---|
| `pause` | running / scheduled | paused | `removeTask` 清 delayed job | 释放 idle | status=paused |
| `resume` | paused | running（有检查点）/ scheduled（从未执行） | `enqueueResumeFromPause`（`fromPause=true`） | 置 working | status=running |
| `cancel` | running / scheduled / paused | canceled（终态） | `removeTask` | 释放 idle | status + **done**（收口） |
| `transfer-to-human` | running / paused / failed | paused（原 running）/ 保持 | `removeTask`（仅 running） | 释放 idle（仅 running） | status=paused（仅 running） |

`resume` 的**检查点分支**（`tasks.service.ts:456`）：

```ts
const fromCheckpoint = task.startedAt !== null;
const nextStatus: TaskStatus = fromCheckpoint ? TASK_STATUS.RUNNING : TASK_STATUS.SCHEDULED;
```

用 `started_at` 是否非空判断是否已产生检查点：已跑过 → 置 `running` 并重投 `fromPause=true`，Runner 侧 `graph.invoke(null)` 从最近检查点续跑当前节点（工具按 `taskId+nodeId` 幂等防重复）；从未执行（在 `scheduled` 时被暂停）→ 回 `scheduled` 全新投递，避免对未执行任务做无意义的「续跑」。

`transfer-to-human` 采用 **append 语义**写交接摘要（`tasks.service.ts:629`）：

```ts
const outputs = [...((task.outputs ?? []) as Record<string, unknown>[]), handoff];
```

`outputs` 为类型化数组 `[{type, payload}]`，交接摘要即一条 `type='handoff'` 记录。同一任务可多次转人工（换承接人 / 追加说明）而不覆盖历史。

### 4.3 幂等设计

- `pause` / `cancel`：已是目标态则直接返回成功（`changed:false`），不抛错、不重复发 SSE；源状态非法 → 409 而非静默成功。
- SSE `cleanup` 用挂在 `subscriber` 实例上的 `__cleaned` 标记做幂等（`task-stream.controller.ts:302`），防止 `finishDone` 与 `req.close` 并发导致连接计数双重递减。
- 队列侧 `jobId=taskId`，BullMQ 天然保证同 id 活跃 job 唯一；`enqueueResume*` 前先 `removeTerminalJob` 清掉终态历史 job，否则 `add` 会被幂等 no-op 静默吞掉（`packages/runtime/src/enqueue.ts:181`）。

### 4.4 retry = 新任务 + 撤销自动重投

`tasks.service.ts:350`：

```ts
// 手动重试前撤销源任务待触发的自动重投 job（04 §5.3）：否则新任务与源任务重投并发跑同一业务
await this.enqueuer.removeTask(taskId, source.type as TaskType);
```

任务队列开启「可重试错误自动重投」（`attempts=3` + 指数退避 30s）。手动重试时**必须先撤销源任务待触发的自动重投 job**，否则新任务与源任务重投会并发跑同一业务 → 重复发邮件 / 重复建线索。

### 4.5 批量操作复用单任务语义

`tasks.service.ts:696`：

```ts
for (const taskId of dto.taskIds) {
  try {
    if (dto.action === 'retry') {
      const r = await this.retry(orgId, userId, taskId);
      results.push({ taskId, ok: true, status: r.status, newTaskId: r.taskId });
    } else {
      const r = await this.transferToHuman(orgId, userId, taskId, { reason: dto.reason });
      results.push({ taskId, ok: true, status: r.status });
    }
  } catch (err) {
    results.push({ taskId, ok: false, error: err instanceof BizException ? err.message : String(err) });
  }
}
```

- **逐条复用单任务方法**，不另写批量逻辑 → 状态机语义只有一个真相源。
- **单条失败不阻断其余**，逐条回传 `ok/error`（部分成功语义，而非整体回滚）。对「批量重试 50 条失败任务」是正确取舍。
- 1..50 的数量上限由 DTO 层 zod 卡住。

### 4.6 日志增量：雪花 ID 即游标

`tasks.service.ts:299`：

```ts
if (after) {
  // Crockford 字典序 = 时间序（雪花游标 02 §8.3）
  conditions.push(sql`${schema.aiTaskLog.id} > ${after}`);
}
```

日志主键是 Crockford 编码的雪花 ID，**字典序等于时间序**，`WHERE id > after` 即天然稳定的增量游标 —— 不需要额外自增 seq，也不受 `occurred_at` 同毫秒并列影响。配 `limit + 1` 探测 `hasMore`，前端可无状态持续增量拉取。

### 4.7 多租户与索引

联合索引均把 `org_id` 放首位，且从接口筛选条件反推：

- `idx_ai_task_org_status(org_id, status, created_at DESC)` → 命中「status Tab 筛选 + 创建时间倒序分页」这一最热查询；
- `idx_ai_task_org_employee` / `idx_ai_task_org_type` → 覆盖另两个筛选维度。

## 5. 暂停机制：协作式中断（API ↔ Worker 如何协同）

### 5.1 结论：不是抢占式 kill，是协作式暂停

API 无法"掐断"Worker 进程里的 LangGraph 执行，因此设计为：**API 只置一个 DB 标志位 + 清队列，Worker 在每个节点开始前主动探测该标志并自我中止**。中断粒度 = **一个 SOP 节点**。

### 5.2 API 侧：只改状态，不动进程

`POST /tasks/:id/pause` → `TasksService.pause`：

```ts
// 事务内：CAS 状态机
const rows = await tx.update(schema.aiTask)
  .set({ status: TASK_STATUS.PAUSED, updatedAt: now })
  .where(and(eq(id, taskId), inArray(status, [RUNNING, SCHEDULED])))
  .returning({ id: schema.aiTask.id });
// 事务内：留痕 + 释放员工位
await tx.insert(schema.aiTaskLog).values({ ..., content: '任务已暂停（恢复后从最近检查点续跑当前节点）' });
await releaseEmployeeIdle(tx, { employeeId, excludeTaskId: taskId, now });

// 事务提交后
await this.enqueuer.removeTask(taskId, result.type);                        // 清 delayed job
await this.publisher.publish(taskId, buildStatusEvent({ status: PAUSED })); // SSE
```

这一步对**正在执行中的节点没有任何影响** —— 没有信号、没有取消令牌，只是把 DB 里的 `status` 从 `running` 改成 `paused`。

`removeTask` 在两种场景下作用不同：

| 场景 | 作用 |
|---|---|
| 任务在 `scheduled`（排队 / 定时，未被 Worker 领取） | **真正阻止启动** —— 摘掉队列里的 job，Worker 永不消费到 |
| 任务在 `running`（已被领取、图在执行） | 基本是 no-op（active job 摘不掉）—— 真正的停止靠下面的 DB 标志 |

### 5.3 Worker 侧：节点入口探测（核心机制）

`GraphCompiler` 在**每个节点执行前**查一次 DB（`compiler.ts:566`）：

```ts
private async beginStep(ctx, node, seq) {
  await withOrg(ctx.db, ctx.orgId, async (tx) => {
    // 节点级暂停探测：DB 中任务已离开 running（API 置 paused）→ 中止
    const [task] = await tx.select({ status: schema.aiTask.status })
      .from(schema.aiTask).where(eq(schema.aiTask.id, ctx.taskId)).limit(1);
    if (task && task.status !== TASK_STATUS.RUNNING) {
      throw new PauseAbortError();
    }
    await tx.insert(schema.aiTaskStep).values({ seq, status: RUNNING, ... })
      .onConflictDoUpdate({ target: [taskId, seq], ... });  // upsert 幂等锚点
  });
}
```

判定条件是 `status !== RUNNING`，而非 `=== PAUSED` —— **任何"离开 running"的情况都会中止**（暂停 / 取消 / 转人工 / 额度耗尽转 paused 共用同一条路径），语义即"我不再被允许继续执行"。

### 5.4 异常如何穿过 LangGraph 被收口

**① `wrapNode` 豁免它，不把步骤落 failed**（`compiler.ts:409`）：

```ts
} catch (err) {
  // 审批挂起 / 外部暂停：步骤保持占位态，不落 failed（终态语义由 runner 收口）
  if (!(err instanceof ApprovalPendingError) && !(err instanceof PauseAbortError)) {
    await this.failStep(ctx, node, seq, err);
  }
  throw err;
}
```

暂停不是错误 → 被中断的步骤不变成红色 failed，而是保持 `running` 占位，**恢复后会重跑它**。

**② Runner 捕获后只清理，绝不覆盖状态**（`runner.ts:192`）：

```ts
if (err instanceof PauseAbortError) {
  await redis.del(heartbeatKey(taskId));                    // 摘心跳（否则 ZombieReaper 会误判）
  await flushBufferedEvents(publisher, taskId, ctx.events); // 把缓冲日志推给前端
  return { status: TASK_STATUS.PAUSED };                    // 不写库、不改状态
}
```

job 正常结束（`return` 而非 `throw`），**不会被 BullMQ 判失败重投**。

### 5.5 双保险：终态写回带状态前置条件

若探测窗口被穿透（节点已进入执行、图随后跑完），`completed` 会不会覆盖 `paused`？不会 —— 终态写回带 `status='running'` 前置条件（`runner.ts:547`）：

```ts
const rows = await tx.update(schema.aiTask)
  .set({ status: COMPLETED, outputs, progressPct: 100, finishedAt: now })
  .where(and(eq(id, taskId), eq(schema.aiTask.status, TASK_STATUS.RUNNING)))  // ← CAS
  .returning({ id });
if (rows.length === 0) {
  return { status: TASK_STATUS.PAUSED };  // 执行期间被外部暂停 → 不覆盖
}
```

`fail` 路径同理。绝不会出现"暂停了却变成已完成"。

### 5.6 为什么恢复能从断点续跑

检查点是 **LangGraph 的 PostgresSaver**，Worker 启动时装配、图编译时传入（`compiler.ts:346`、`worker/src/index.ts:127`）：

```ts
const graph = wf.compile({ checkpointer: this.deps.checkpointer });
// invoke: configurable: { ctx, thread_id: ctx.taskId }   ← thread_id 就是 taskId
```

`thread_id = taskId`，PostgresSaver 在**每个超步（节点）完成后**把完整 State 落盘（独立 `langgraph` schema 4 张表）。因此：

- 暂停发生在节点 N 执行中 → 检查点里是**节点 N 之前**的状态；
- 恢复时 `enqueueResumeFromPause(fromPause=true)` → `claim` 把 `paused→running` → `graph.invoke(null)` 从检查点恢复 State，**重跑节点 N**（`runner.ts:164`）。

**重要推论**：被中断的当前节点会**从头重跑一遍**（它没写完检查点），所以工具必须按 `taskId + nodeId` 幂等，否则恢复一次就重复发一封邮件。

### 5.7 暂停时序

```
API                          PostgreSQL              Worker (LangGraph)
 │                                                      │ 节点 N 执行中（LLM 调用 30s）
 │ CAS running→paused ──────> [ai_task: paused]         │
 │ 写日志 / 员工回 idle ────>                            │
 │ removeTask(清 delayed)                               │
 │ PUBLISH status=paused ──> 前端收到                    │
 │                                                      │ 节点 N 跑完
 │                                                      │ beginStep(N+1) → SELECT status
 │                                                      │   → 'paused' ≠ running
 │                                                      │ throw PauseAbortError
 │                                                      │ wrapNode 豁免（不落 failed）
 │                                                      │ runner: del 心跳 + flush 事件
 │                                                      │ job 正常结束（不重投）
```

### 5.8 取舍

| 取舍 | 说明 |
|---|---|
| 为什么不做抢占式中断 | Node 里没有线程 / 信号可杀；LLM 调用是外部 HTTP，强行 abort 只会导致状态不一致。协作式把"何时停"交给安全的检查点边界 |
| 为什么探测放 `beginStep` 而不放节点内部 | 节点边界是唯一有检查点保护的安全点；节点中间停下会导致 State 半更新，恢复后数据错乱 |
| 为什么用 `status !== RUNNING` 而非 `=== PAUSED` | 取消、转人工、额度耗尽共用同一条中止路径，避免漏判 |
| 代价 | ① 暂停延迟上限 = 当前节点剩余执行时间（LLM 节点 30s 则最坏等 30s）；② 中断节点恢复后重跑 → 工具必须幂等；③ 每个节点多一次 DB 查询（与步骤 upsert 同事务，可忽略） |

`cancel`（终态 canceled）与 `transfer-to-human`（running 时置 paused）**复用同一条 `PauseAbortError` 通道** —— "外部让任务停下来"只有一种实现，符合"语义只有一个真相源"。

## 6. SSE 实时流设计

核心矛盾：**事件源在 Redis Pub/Sub（易失、不重放），历史在 PostgreSQL（可靠、可回放）**，两者拼接必然存在竞态。方案是「订阅先行」+ 四道补丁。

`task-stream.controller.ts` 主流程：

```
① 读任务行（仅 404 校验，status 此时不定稿）
② 连接上限检查（单用户 ≤10 / org ≤200，超限 42901）→ 计数 +1
③ flush 响应头，开流（RawResponse + text/event-stream + X-Accel-Buffering: no）
④ 【订阅先行】SUBSCRIBE task:{id}:events   ← 必须先于回放，否则订阅前的事件全丢
⑤ 回放：after 游标分页读日志（200/批，最多 5 轮 = 1000 条）→ 按 logId 去重发送
   订阅成功后再读一次任务行定稿 status；已终态 → 补发 status + done 并关闭
⑤.5 启动 5s 终态兜底轮询
⑥ 15s 心跳 + req.close 清理
```

四个补丁各自弥合一个真实故障窗口：

| 补丁 | 弥合的问题 |
|---|---|
| **订阅先行 + 回放**（M3-09） | 先回放后订阅 → 中间 PUBLISH 的日志永久丢失；反过来则被「回放」与「订阅回调」双收 → 用 `sentLogIds` Set 按 `logId` 去重 |
| **订阅后重读 DB 定稿 status**（M3-03） | ① 读到 `running` 之后、订阅成功之前 Worker 提交了终态。Worker 是「先提交事务再 PUBLISH」，此刻 DB 终态必已可见 → 重读即可兜住，杜绝客户端收不到 done 挂等心跳 |
| **5s 终态兜底轮询**（M3-11） | Worker「commit 终态 → PUBLISH done」之间**崩溃** → 实时通道与回放都不含该 done。周期重读 DB，发现终态且本连接未发过 done → 补发并关闭 |
| **`cleanup` 幂等**（M3-10） | `subscribe` 抛错 / `finishDone` / `req.close` 三条路径都要回收连接计数，用标记防重入，避免泄漏 |

**统一出口 `finishDone`**：回放、兜底轮询、实时到达三条路径都汇聚于此 → `done` 一经投递立即停轮询、停心跳、关流。保证客户端语义唯一（收 `done` 即结束），不会出现「收到 done 还在等心跳」。

工程细节：

- **事件契约同构**：回放取自 DB 行、实时取自 PUBLISH 消息，统一成 `{type:'log', payload:{logId, time, type, content, leadId?}}`，客户端只按 `payload.logId` 去重，无需区分来源。
- **连接上限为进程内 Map 计数**（`task-stream.controller.ts:41`），注释明确标注 MVP 单实例假设，多实例需换 Redis 计数。

## 7. 完整链路时序

以「新建任务 → 实时看日志 → 中途暂停 → 恢复」为例：

```
POST /tasks
  └─ Service.create
      ├─ tx: 校验员工 → 查员工占用 + org running → insert(status=scheduled)
      └─ commit 后: enqueueTask(jobId=taskId) → 返回 {taskId, status:'running'}

GET /tasks/:id/stream (SSE)
  └─ 订阅 → 回放历史日志 → 重读 DB 发 status → 实时转发 log/progress → 15s 心跳

Worker: claim (scheduled→running + started_at) → 执行图 → 写 log/step → PUBLISH
  → API 转发 → 前端增量渲染

POST /tasks/:id/pause
  └─ tx: CAS running→paused + 写日志 + 员工回 idle
  └─ commit 后: removeTask(清 delayed job) + PUBLISH status=paused
  → Worker 在下个节点探测到离开 running → PauseAbortError 中止，保留检查点

POST /tasks/:id/resume
  └─ tx: started_at 非空 → paused→running + 员工 working
  └─ commit 后: enqueueResumeFromPause(fromPause=true) + PUBLISH status=running
  → Runner invoke(null) 从检查点续跑，工具按 taskId+nodeId 幂等
```

## 8. 取舍与可改进点

**做对的地方**

1. **状态机 + CAS + 提交后副作用**三段式，把「数据库事务」与「不可回滚的外部副作用」边界划清。
2. **批量复用单任务**、`retry` 复用 `create` —— 语义只有一个真相源。
3. 每个补丁标注对应**真实故障编号**（M3-01/03/09/10/11），注释写「根因」而非「做了什么」。
4. 跨进程共享队列 / 事件契约（runtime 包 + zod schema），避免 API / Worker 漂移。
5. **暂停用协作式中断 + 终态 CAS 双保险**：API 只置标志，Worker 在安全的检查点边界自我中止（§5），既保住状态一致性又无需跨进程 kill。

**待改进项**

| 项 | 现状 | 建议 |
|---|---|---|
| SSE 连接计数 | 进程内 `Map`，多实例失效 | 多实例部署前必须换 Redis 计数（注释已标注） |
| 操作留痕日志 `type` | pause/resume/cancel/transfer 均写 `type:'error'` | 语义上不是错误，建议扩展 `task_log_type` 增加 `system`/`action`，否则前端日志流会把操作留痕染红 |
| 批量串行 | `for...of` 逐条 | 量大时可加并发上限（如 5）并保持逐条语义 |
| 并发判定 | 事务内 `count` 快照，无锁 | 当前由 Worker claim CAS 兜底，正确；若要求严格不超发，需 `SELECT ... FOR UPDATE` 或 Redis 令牌桶 |
| SSE 回放上限 | 最多 5×200=1000 条 | 超限静默截断，前端需靠 `/logs` 补拉；可考虑下发「历史过多」提示事件 |
| 暂停粒度 | 节点级协作式中断，延迟上限 = 当前节点剩余耗时 | 长耗时节点（大批量 LLM / 邮件群发）可考虑节点内分段探测 |
| `transfer-to-human` 的 `assignee` | 仅留痕不派单（P1 范围） | 符合 MVP 定位，注释已明示 |

## 9. 一句话总结

这是一个**「控制面做薄、把正确性交给状态机 CAS 与 Worker 侧检查点、用显式补丁弥合每个分布式竞态窗口」**的任务中心设计 —— 不追求理论强一致，但在每一处都清楚标注了「为什么这么做」与「代价是什么」。
