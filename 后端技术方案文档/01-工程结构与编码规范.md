## 1. Monorepo 结构

pnpm workspace + Turborepo，在 Runtime 总纲 §6 骨架上补齐集成层与共享 schema：

```text
tradepilot/
├── apps/
│   ├── api/                    # NestJS：REST、SSE 网关、鉴权
│   │   └── src/
│   │       ├── main.ts
│   │       ├── app.module.ts
│   │       ├── common/         # 过滤器/管道/拦截器/守卫（§4）
│   │       ├── context/        # RequestContext（ALS）：orgId/userId/role/scope/traceId
│   │       └── modules/        # 按域拆分（§3）
│   └── worker/                 # BullMQ Worker + Scheduler + Cron 扫描器
│       └── src/
│           ├── main.ts         # bootstrap：注册队列 worker + 定时器
│           ├── scheduler/      # follow_up 扫描、排队启动（04）
│           ├── cron/           # 审批超时、邮箱同步、额度重置（04/06）
│           └── queues/         # 队列注册与处理器装配
├── packages/
│   ├── db/                     # Drizzle schema、迁移、RLS 策略、种子（02）
│   ├── shared/                 # 枚举常量、Zod schema、SSE 事件契约、Insight 类型
│   │   └── src/
│   │       ├── enums/          # task_status / approval_type / ...（对齐 ER §4）
│   │       ├── contracts/      # API DTO zod + 推断类型（前后端同源）
│   │       ├── insight/        # Insight Schema（接口总览 §4.1）
│   │       └── sse/            # log/progress/status/done 事件类型
│   ├── runtime/                # TaskRunner / Memory / Approval Gate / LLM Gateway（05）
│   ├── tools/                  # Tool Registry 与内置工具（05 §3）
│   ├── workflows/              # 各 task_type 图定义 + promptRef 提示词
│   ├── integrations/           # 邮箱驱动、搜索/抓取、嵌入、对象存储适配器（06/07）
│   └── core/                   # ID 生成、错误码、时区窗口工具、令牌桶、加密
├── docker/                     # compose 文件与 Dockerfile
├── turbo.json / pnpm-workspace.yaml / tsconfig.base.json
└── .github/workflows/          # CI/CD（09）
```

**依赖方向（单向，禁止反向）**：`apps/* → packages/*`；`runtime → tools/workflows/db/core/shared`；`tools → integrations/core/shared`；`shared` 与 `core` 为零依赖底层。

- **前端为独立单应用工程（非 monorepo，见 [前端技术方案文档/01](../前端技术方案文档/01-工程架构与规范.md)）**，本 monorepo 不含前端代码；契约同步以接口文档为权威，`packages/shared/contracts`（Zod schema）可选导出 OpenAPI 供前端对照，前端侧不直接消费本仓类型。

## 2. TypeScript 与构建约定

| 项 | 约定 |
|---|---|
| tsconfig | `tsconfig.base.json` 统一 `strict`、`noUncheckedIndexedAccess`、`module: NodeNext`；各包仅覆盖 paths |
| 模块系统 | ESM（`"type": "module"`）；NestJS 10 以 SWC 构建提速 |
| 路径别名 | `@tradepilot/shared` 等包名直引，不使用相对路径跨包引用 |
| 产物 | apps 构建为独立 bundle（esbuild/tsc）；packages 内部走 workspace 直链，不发布 npm |

## 3. NestJS 模块划分（apps/api）

按接口文档 01～16 的模块边界一一对应，每个域模块内含 `controller / service / dto / repository`：

| 域模块 | 对应接口文档 | 要点 |
|---|---|---|
| `auth` | 16 §1.1 | 登录/注册/邀请接受（[03](./03-认证授权与多租户.md)） |
| `org` / `member` | 16 §1.2–1.4 | 企业信息、成员管理、外发规则（send_rules） |
| `settings` | 16 §1.5–1.8 | 邮箱连接、权限矩阵、通知设置、AI 模型配置 |
| `ai-employee` | 02 | 员工 CRUD、暂停/恢复、KPI 聚合、currentTask 轻量聚合 |
| `task` | 14 | 统一任务接口 + 日志增量 + SSE 订阅端点 |
| `lead` | 03 | 获客工作台、lead-tasks、发现列表、add-to-crm |
| `customer` / `contact` | 04 / 05 | CRM、阶段推进（AI 禁调）、软删、批量操作 |
| `conversation` / `message` | 06 | 会话列表（mailboxId 过滤）、Copilot、草稿、发送 |
| `follow-up` | 07 | 策略/步骤 CRUD、apply、跟单任务列表 |
| `knowledge` | 11 | 上传、分类、索引状态、删除（软删级联 chunk） |
| `approval` | 12 | 汇总/列表/处置（approve/reject/edit） |
| `product` / `quote` / `order` | 08 / 09 / 10（P1） | 产品、报价、订单、转订单、进度填报 |
| `report` / `data-center` | 13 / 15（P1） | 经营报告、发现、指标聚合 |
| `dashboard` | 01 | KPI 聚合（只返回已启用模块 metric） |
| `open-api` | 16 FR-11（P1） | API Key 鉴权 + scopes + Webhook 管理 |
| `sse` | 14 §3.4 | SSE 网关（横切模块，被 task 复用） |

**Controller 规范**：薄壳——只做参数解析（Zod pipe）与调用 service；**Service** 承载业务与事务边界；**Repository** 仅封装 Drizzle 查询（[02 §8](./02-数据访问层设计.md)）。路由路径、响应字段严格按接口文档，不自行增删。

## 4. 横切机制

### 4.1 统一响应与错误

```typescript
// common/filters/http-exception.filter.ts —— 全局唯一出口
// BizException(code: ErrorCode, message?, extra?) 映射接口总览 §2.5 错误码
{ code: 0, message: 'ok', data: { }, traceId: 'trc_xxx' }
```

- `code=0` 由 TransformInterceptor 包装；列表接口 `data` 固定 `{ items, total, page, pageSize }`。
- 错误码集中在 `packages/core/error-codes.ts`（40001/40101/40301/40401/40901/42201/42901/50001/50301），HTTP 状态码按映射表返回；LLM/邮箱/外部数据源不可用统一 `50301`。
- 未捕获异常 → `50001` + pino error 日志（含 traceId），不向客户端泄露堆栈。

### 4.2 请求上下文（ALS）

`RequestContextService` 基于 `AsyncLocalStorage` 携带 `{ traceId, orgId, userId, role, scope }`：

- traceId 生成于中间件（`trc_` 前缀），写入响应头与 pino 绑定；
- orgId/userId/role 从 JWT 解出（**接口不传 orgId**，总览 §2.1），下游 repository / 工具调用全部从此读取；
- worker 侧由 TaskRunner 构造同名上下文（`orgId` 来自任务行），保证 packages 层代码两侧一致。

### 4.3 校验

- 入参：全局 `ZodValidationPipe`，DTO 即 `packages/shared/contracts` 中的 Zod schema（`z.infer` 出类型），失败 `40001` + 字段级 detail。
- 出参：聚合/产出类接口（Insight、outputs）在 service 层经 Zod parse 后再返回，防脏数据出网。

### 4.4 分页与筛选

- 统一 `page/pageSize(≤100)/keyword/sortBy/sortOrder` 查询参数（总览 §2.3），由 `PaginationDto` 解析；
- 日志类增量接口例外：`after={logId}` 游标（雪花时序），见 [02 §8.3](./02-数据访问层设计.md)。

### 4.5 配置管理

- 环境变量经 Zod schema 校验后注入 `ConfigService`（缺失/不合法 fail-fast）；清单见 [09 §4](./09-部署运维与可观测性.md)。
- 业务配置（org 级）一律读库（`org.send_rules`、`ai_model_setting` 等），**不进环境变量**；Scheduler 每次入队前实时读取（16 FR-12）。

## 5. 日志规范

| 项 | 约定 |
|---|---|
| 库 | pino（JSON 结构化），`nestjs-pino` 请求日志自动绑定 traceId |
| 级别 | `error`（需处理）/ `warn`（降级、额度超限、重试）/ `info`（业务关键动作）/ `debug`（开发） |
| 字段 | `traceId, orgId, taskId?, employeeId?, module, msg`；禁止打印凭据、邮箱明文、token |
| 外呼 | 每次外部调用（LLM/搜索/邮箱）记 `warn/info` 级耗时与结果码，与 `ai_task_log` 业务留痕分离 |

## 6. 编码与错误处理约定

1. **错误**：service 层 `throw new BizException(...)`；禁止裸 `HttpException` 与魔法数字 code。
2. **事务**：跨表写必须在 service 层一个事务内完成（如审批处置级联、注册种子）；单表写可不包事务。
3. **幂等**：所有对外的写操作接口与队列处理器都要声明幂等键来源（任务域 `taskId+nodeId`，邮箱同步 `external_message_id`，见 [04 §5](./04-任务调度与队列.md)、[06 §2](./06-外部集成设计.md)）。
4. **时区**：库层一律 UTC；仅 `packages/core/time-window.ts` 提供「org 当地日历日 / 发送窗口对齐」函数（频控顺延公式唯一实现，Scheduler 与 `schedule_next` 共用）。
5. **枚举**：TS 侧只用 `packages/shared/enums` 的常量对象（值与 ER §4 一致），不得散落字面量。
6. **AI 身份**：涉及 `operator_type` 的写路径，统一在 service 层从上下文判定 `ai|user`，不落参数。

## 7. 测试策略

| 层 | 工具 | 范围 |
|---|---|---|
| 单元 | Vitest | service 逻辑、图节点纯函数（`progressOf`、窗口对齐、频控公式）、Zod schema |
| 集成 | Vitest + Testcontainers（PG16+pgvector / Redis7） | repository、RLS 生效性（跨 org 查询必须为空）、事务级联、BullMQ 处理器 |
| E2E | supertest | 关键链路：注册种子→登录→建获客任务→SSE 事件→审批 approve→完成 |
| 契约 | 接口文档快照测试 | 每模块至少 1 个黄金用例锁定响应结构，防契约漂移 |

- 覆盖率门槛：`packages/core`、`packages/runtime`（Gate 分流、重试、窗口对齐）≥ 80%；apps 层不设硬门槛。
- 测试数据工厂集中在 `packages/db/testing`（org/customer/task 模板函数）。

## 8. Git 与 CI 门禁

- 分支：`main` 保护；功能分支 `feat/<module>-<slug>`；PR 必须过 CI（见 [09 §5](./09-部署运维与可观测性.md)）。
- 提交：Conventional Commits（`feat/fix/chore/docs(ref)...`），CHANGELOG 由 CI 生成。
- Pre-commit：lint-staged（prettier + eslint）+ `drizzle-kit check`（迁移与 schema 一致性）+ tsc 全仓类型检查。
- 禁止提交：`.env`（提供 `.env.example`）、任何真实凭据（[08 §2](./08-安全设计与合规.md)）。
